The plan — in very simple English

We are building a local troubleshooting team made of AI agents.

We give Resolve a folder of company files. The agents read them, compare what happened with the SOPs and rules, connect the dots, challenge each other, and give a clear recommendation with evidence. Everything runs on the Dell GB10. Nothing needs to leave the machine.

What started the ideaRCA: when something goes wrong, how do we find out why?

Instead of building a semiconductor-only RCA tool, the idea is to keep the troubleshooting pattern and let the same engine work across engineering, finance, operations, manufacturing, supply chain and other business problems.

The key ideaThe engine stays the same. The case pack changes.

Change the files, allowed tools and domain instructions. The same five roles can investigate a different business problem without rebuilding the whole system.

01 · What Resolve actually is

It is not a finance agent. It is not a supply-chain agent. It is a troubleshooting engine.

Most difficult company problems have the same shape: information is scattered, different teams see different pieces, an SOP covers part of the problem, and somebody still has to decide what to do next.

Input

Local company files

Logs, SOPs, contracts, spreadsheets, machine data, incident notes, deployment records, finance data, policies or whatever the case needs.

Work

Agents connect the dots

They read different evidence, work in parallel where useful, test the first answer and identify what is still missing.

Output

A recommendation you can inspect

What happened, why it probably happened, what evidence supports that view, what to do next, what is risky, and what still needs a human.

The simple product sentence: SOPs handle the normal path. Resolve helps with the messy exception that falls between them.
02 · The five-agent team

Five different jobs. They do not endlessly chat with each other.

Each agent gets a small task and writes a structured finding into one shared case record. That shared record is how the agents “talk.” This is much easier to control than a free-form group chat.

01

Evidence Scout

What do the local files actually say?

02

Technical / Operations

What is happening, and what can we safely test?

03

Business Impact

What does this cost? What matters to the company?

04

Red Team

Why might the first answer be wrong?

05

Judge

Do we know enough to recommend or act?

Agents do reasoning.

They read, summarize, form hypotheses, compare documents and challenge assumptions.

The runtime controls action.

The model does not get to give itself permission. The code checks the evidence, action scope, approval and verification rules.

Use evidence IDs. Do not invent facts. Challenge the leading answer. Ask for missing information. Do not execute consequential actions without the contract.

What world are we troubleshooting?

A semiconductor case gets tool logs, yield data and process SOPs. A finance case gets transaction logs and routing rules. A supply-chain case gets inventory, supplier, transport and demand data.

04 · The Resolve Contract

Before a recommendation becomes an action, it has to pass a very simple check.

1

Evidence

Do we actually have enough facts?

2

Authority

Is this action allowed? Does a human need to approve it?

3

Consequence

What happens if we are wrong?

4

Reversibility

Can we safely undo it?

5

Rehearsal

Can we test the plan locally before doing it?

6

Verification

After we act, how do we know it actually worked?

Important: if evidence is missing, Resolve does not simply ask the model the same question again. It sends an agent to find the exact missing evidence.

Historical market-access replay

A publicly documented 2012 deployment incident produced 97 pre-market error messages and one server was not correctly updated. We recreate the decision pattern with synthetic local files.

A true supply-chain / logistics case

A critical material shipment is delayed nine days at a port. The plant has four days of stock left. Alternate suppliers exist, but approvals and customer/product constraints differ.

06 · Why the architecture came first

The business case changes. The reasoning pattern is the more fundamental thing.

Why this was useful

Build the reusable engine once

If the core can read evidence, challenge assumptions, ask for missing facts, rehearse a plan and verify an outcome, we can swap in different domain packs without rewriting the entire product.

What changes now

For the hackathon, lock one primary demo early

The generic architecture is useful, but judges need one story they can understand in 60 seconds. We will build one case beautifully, then use the other cases only to prove that the engine generalizes.

Simple analogy: Resolve is the operating system. The semiconductor RCA, payment incident, order exception and supply-chain problem are apps/case packs running on top of it.
07 · One model first, not two

Five agents do not require five models. They are five roles using one local brain.

We moved to one model as the starting point because the hackathon is won by a reliable live demo. One stable local model can run all five roles. A second model is useful only after the whole product already works.

P0 · One model

Goal: make the full demo work through the NVIDIA stack. The five agents use different instructions and tool permissions but share the same local model.

Unsloth: think of it as a source of optimized/quantized Qwen model files. If an Unsloth Qwen GGUF runs cleanly through the local serving stack, we can use it. If not, we use the NVIDIA-validated local model profile.

→

P1 · Optional second model

Only after P0 works. Model 2 can be a fast worker, a fallback when model 1 errors, or a challenger when the first model is stuck on the same hypothesis.

Important: we never ask model 2 repeatedly until somebody says “yes.” Model disagreement means more evidence or human review.

08 · Win tactics

We are not trying to build the biggest system. We are trying to build the most convincing working demo.

01Live demo first

One complete local run beats ten unfinished features.

02Show the sponsor stack

OpenClaw, NemoClaw, OpenShell and GB10 should be visible in the product, not hidden in a slide.

03Show business impact

Put dollars, downtime, yield or customer impact on screen so a nontechnical judge understands why it matters.

04Counterfactual A/B

Change one evidence file and show that the same engine can reach a different answer. This proves it is not a scripted movie.

05Judge can approve

If allowed, let a judge press APPROVE. Their action appears in the journal.

06Live GB10 numbers

Show local runtime or model timing so the hardware is clearly part of the story.

07Rubric map

Every judging criterion must have a visible proof in the demo or submission.

08Backup everything

Live run → one-model fallback → real successful replay → recorded GB10 video.

The final idea

Resolve is a local troubleshooting engine for messy business problems.

Give it the right local files and a case-specific skill pack. The same core reads the evidence, connects it to the SOPs and constraints, challenges the first answer, asks for what is missing, and returns a recommendation that a human can inspect. For the hackathon, we prove that with one beautiful live case — then show that the same engine can move to RCA, engineering, finance, operations or supply chain without rebuilding the architecture.
