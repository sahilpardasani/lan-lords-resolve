# 1\. The most important red-team finding: don't reuse the Autonomous Labs implementation

The rules you pasted explicitly say that starter scaffolds and existing libraries are acceptable, but that the agent/system itself must be built during the event and materially prebuilt work can lead to disqualification.

Your existing Autonomous Labs already has sophisticated concepts such as:

Define → Check → Rehearse → Run → Review → Reuse, evidence records, bounded workflows, approval controls, verifier-first improvement, orchestration, tool registries, security boundaries, etc.

Those ideas are excellent.

Do not copy the implementation.

For the hackathon:

* new repository at kickoff  
* new application name  
* new UI  
* new orchestration implementation  
* no copied AL modules  
* no copied graph editor  
* no copied APIs  
* no copied prompt library  
* no 43-block ecosystem  
* no multi-tenant infrastructure  
* no company-specific private data  
* no existing AL frontend

Use the ideas and engineering lessons, not the code.

That keeps the entry both much simpler and much easier to explain.

# 2\. What I would actually build

Tentative name:

## LocalOps Lab

### Private AI that investigates, tests, acts and verifies.

The exact name can change. The architecture matters more.

### Golden demo scenario

Give it a simulated corporate incident:

“Checkout failures jumped from 1% to 18% after today's deployment. Investigate the problem and restore the service without making an unsafe production change.”  
You provide a local workspace containing:

* application source  
* logs  
* deployment history  
* configuration  
* test suite  
* local service/container  
* internal runbook  
* a few historical incident notes

Then the system operates.

### Phase 1 — DEFINE

It turns the request into an Objective Contract:

Goal

* reduce checkout errors below 2%

Constraints

* don't expose internal logs  
* don't delete customer data  
* don't alter payment data  
* changes must be reversible

Success test

* integration suite passes  
* health endpoint passes  
* error rate simulation returns below threshold

Already much better than:

“Agent, please fix my server.”

# 3\. The agent architecture

Do not create 10 agents.

Use four logical roles.

### 1\. Coordinator

Understands the goal.

Creates the plan.

Assigns bounded tasks.

Maintains the authoritative state.

### 2\. Investigator

Reads:

* logs  
* code  
* configs  
* local documentation  
* optionally permitted internet sources

Produces:

* hypotheses  
* evidence  
* confidence  
* missing information

### 3\. Operator

Can:

* inspect shell  
* edit a sandbox copy  
* run tests  
* create patches  
* perform reversible actions

It cannot independently authorize consequential execution.

### 4\. Verifier

Critically important.

The verifier does not merely ask:

“Does the solution sound good?”  
It evaluates independently:

* tests  
* metrics  
* requirements  
* changed files  
* rollback ability  
* side effects  
* evidence

And returns:

PASS

FAIL

or

INSUFFICIENT EVIDENCE

That last state is important.

# 5\. The killer feature isn't “agents”

It is this:

## Proposal → rehearsal → independent verification → permission → action → outcome verification

Most hackathon agent demos will probably look like:

question → LLM → tools → answer.  
Yours should visibly look like:

objective → evidence → hypothesis → experiment → verification → approval → action → proof.  
That is materially different.

# 10\. Model choice on the GB10

I would not start the hackathon by experimenting with exotic models.

## Primary

### Qwen3.6-35B-A3B-NVFP4

NemoClaw's current DGX Spark managed-vLLM configuration lists this as the Spark default. NVIDIA's profile includes:

* NVFP4  
* local vLLM  
* 262K maximum context  
* 4 concurrent sequences  
* prefix caching  
* chunked prefill

That's almost exactly what you need.

### Backup 1

Qwen3.6-27B-FP8

Also a supported DGX Spark profile. 

### Backup 2

NVIDIA-Nemotron-3-Nano-4B-FP8

Much smaller.

Good emergency mode if something breaks.

NemoClaw currently supports that local profile as well. 

### Optional experiment

The August 11 NemoClaw release added an experimental Nemotron 3.5 Lightning 30B-A3B NVFP4 single-DGX-Spark profile. Interesting, but I would not make an experimental configuration your competition-critical path unless it proves rock solid in testing.

# 11\. Your Bonsai 27B model is interesting — but I wouldn't make it the competition model

The Ternary Bonsai model you supplied is legitimately useful for your Mac preparation.

The model card reports:

* \~7.2 GB deployed model  
* Metal support  
* MLX version  
* 262K context capability  
* 27B-class model

More importantly for your 18 GB M3 Pro, the model card reports around 8.4 GB peak at 4K context and 8.7 GB at 10K, with much greater memory consumption at long context. With 4-bit KV compression it claims about 10.1 GB at 100K and 12.8 GB at full 262K context. 

So:

### Yes

Your M3 Pro can plausibly run Bonsai locally.

### No

I would not run:

* Bonsai 27B  
* Docker/Colima  
* NemoClaw  
* your IDE  
* browser  
* dashboard

all aggressively at once on 18 GB.

You'll get memory pressure.

Also, the model's own card explicitly says long-horizon multi-file agentic coding is not yet a strong target for this release. 

So my strategy is:

Bonsai \= useful local reasoning/model experiment.

Smaller model \= Mac full-stack rehearsal.

# 25\. Hard limits

Every run gets:  
maximum agent turns:       12  
maximum hypotheses:         3  
maximum candidate fixes:    3  
maximum verifier retries:   2  
maximum shell timeout:     30s  
maximum network domains:    allowlist

maximum concurrent agents:  2  
Why only two concurrent?

Because local inference concurrency is not free.

Four “agents” simultaneously hitting one model generally creates contention rather than four times the intelligence.

NVIDIA's current managed Qwen Spark profile supports four concurrent sequences, but that doesn't mean your product should continuously saturate all four. 

Use concurrency for:

* independent evidence gathering

Use serialization for:

* decisions  
* candidate selection  
* execution  
* verification  
* state commits

is this just an analyst work?

If we stop at “read local company files → synthesize them → give a recommendation”, then yes: that is basically an AI analyst, just with multiple agents.

That is the risk in the current framing.

What makes Resolve meaningfully different is that it should not merely *analyze the problem*. It should work the problem.

Think of the progression like this:

| Level | What it does | Example |
| ----- | ----- | ----- |
| Analyst | Reads information and explains it | “Yield dropped because chamber temperature changed.” |
| Investigator | Actively searches for missing evidence | “I need recipe history, maintenance logs and affected-lot data. I’ll retrieve and correlate them.” |
| Troubleshooter | Generates hypotheses and runs tests to distinguish between them | “If chamber drift caused it, control-lot replay should reproduce the defect. Run test.” |
| Operator | Takes a bounded action | “Isolate Tool 4 and revert recipe version 17.” |
| Closed-loop agent | Checks whether the action actually fixed reality | “Yield recovered to 96.8%; hypothesis supported; keep Tool 4 isolated pending maintenance.” |

Resolve should sit primarily at levels 2–4, with level 5 verification.

That is much more interesting.

### The product is not “five analysts”

For example, suppose a semiconductor line suddenly loses yield.

A normal AI analyst might read ten documents and say:

“The likely root cause is chamber pressure drift after maintenance.”

Useful, but not particularly special.

Resolve should do:  
Yield drops  
    ↓  
Observe local evidence  
    ↓  
Generate 3 competing hypotheses  
    ↓  
What evidence would distinguish them?  
    ↓  
Run local queries / tests / simulations  
    ↓  
Kill 2 hypotheses  
    ↓  
Find remaining uncertainty  
    ↓  
Recommend bounded intervention  
    ↓  
Rehearse intervention  
    ↓  
Human approves if consequential  
    ↓  
Apply / simulate  
    ↓

Measure outcome

That's a troubleshooting loop.

The LLM isn't valuable merely because it writes the explanation. It's valuable because it decides:

“What should I inspect next to reduce uncertainty?”

That distinction is critical.

## The five agents make more sense under this framing

I would slightly change how we've been describing them.

Evidence Scout isn't an analyst. It actively searches local sources for facts relevant to competing hypotheses.

Investigator / RCA Agent develops and tests causal hypotheses.

Operations Agent figures out what diagnostic tests or bounded interventions are possible.

Red Team tries to falsify the current diagnosis.

Judge decides whether enough evidence exists to recommend the next move.

Business impact becomes a tool/capability available to the system, rather than necessarily consuming one of your five most important agent slots.

That may actually be better for the product.

# Your $2.4M case is slightly different

This is why you may have felt the concept becoming fuzzy.

Nothing necessarily “broke.”

Instead:

Resolve has to find a feasible plan under conflicting constraints.

That's still compatible with the architecture, but it's a different subtype.

# Resolve \= local exception & troubleshooting engine

And underneath it:  
Troubleshoot  
"What is wrong and what should we do?"

Resolve  
"Given conflicting constraints, what should we do?"

Recover

"Something failed; what is the safest next action?"

Same engine.

Different case.

# This is also why building the architecture first was not inherently wrong

You were trying to identify the reusable primitive.

The primitive isn't:

Financial analysis.

It isn't:

Supply chain.

It isn't:

Semiconductor RCA.

It is:

An agent repeatedly reduces uncertainty until it can justify a next action.

That is a genuinely broader architecture.

Where you need to be careful is the hackathon presentation.

Don't explain all of this before the demo.

For the judges:

“Resolve is a local AI troubleshooter. Give it the files your company already has. It investigates what went wrong, figures out what it needs to know next, tests competing explanations, and recommends the safest next step.”

Then show one case.

After the demo:

That's enough.
